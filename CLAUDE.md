# CLAUDE.md

Guidance for Claude Code (or any agent) working in this repo.

## What this is

MacMic: a native macOS menu bar app (Swift + SwiftUI + IOKit/IOUSBHost) that drives the RGB lighting on a HyperX QuadCast S microphone, which has no native macOS host software. Full background and protocol details: [README.md](README.md) and the implementation plan at `docs/plans/completed/20260720-macmic-rgb-control.md`.

## Build & test commands

Pure SwiftPM package — no `.xcodeproj`. Run everything from the repo root.

```sh
swift build                       # debug build, all targets
swift build -c release            # release build (needed for the app bundle and CLI hardware use)
swift test                        # run the full QuadcastKitTests suite
swift test --filter FrameTests    # run one test suite
./scripts/make-app.sh             # release build + assemble dist/MacMic.app (ad-hoc signed)
./scripts/test-make-app.sh        # shellchecks make-app.sh, runs it, asserts the built bundle looks right
swift run macmic-cli probe        # hardware diagnostic: lists matched USB services + which accepts control transfers
swift run macmic-cli audio status # hardware diagnostic: Core Audio gain/mute + monitoring volume/mute of the mic
swift run macmic-cli audio test   # hardware diagnostic: 10 s mic pass-through to the default output + level meter (--seconds N); --record N records N s then plays it back
```

There is no separate lint step; `swift build` must be warning-free (checked in Task 10 of the plan).

## Architecture

```
MacMic (SwiftUI MenuBarExtra menu + one sidebar-navigation Window (Lighting, Audio, Device), .accessory — no Dock icon)
  └─ AppState (composition root: builds the concerns below, opens the shared AudioDeviceControl, fans out sleep/wake; publishes nothing)
       ├─ Lighting (lighting settings persisted as one blob, presence, send health + retry over HIDTransport/FrameStreamer)
       │    ├─ LightingSettings (pure value: mode + each mode's remembered payload, brightness, enabled — every lighting invariant)
       │    └─ LightingSettingsStore (the blob in UserDefaults; one-time migration of the pre-blob per-field keys)
       ├─ AudioControls (mic gain/mute + monitoring volume/mute over AudioDeviceControl; echo reconcile; not persisted)
       ├─ MicrophoneTest (the Audio page's Test Microphone model over MicrophoneTestSession; stops on page exit and sleep)
       └─ QuadcastKit
            ├─ FrameStreamer (55 ms display loop on Scheduler)
            ├─ PresetSequencer (LightMode → [Frame])
            ├─ QuadcastPacket / Frame / RGBColor (pure, byte-exact protocol types)
            ├─ HIDTransport (protocol) — lighting
            │    ├─ IOUSBHostTransport (raw USB control transfer — the transport that actually works, see below)
            │    ├─ QuadcastFunctionSet (internal: the matched USB functions, send order, "removed once all are gone")
            │    └─ MockHIDTransport (test target only)
            ├─ Scheduler (protocol) — time seam: DispatchScheduler in production, ManualScheduler (test target only); used by FrameStreamer, Lighting's retry, MicrophoneTestSession and the CLI's MicrophoneTestRun
            ├─ AudioDeviceControl (protocol) — mic gain/mute, headphone-monitoring volume/mute; multi-observer; HAL device ids internal to the snapshot
            │    ├─ CoreAudioDeviceControl (Core Audio HAL properties, observed live)
            │    │    └─ HALPort (internal protocol) — SystemHAL (the real HAL), FakeHAL (test target only)
            │    └─ MockAudioDeviceControl (test target only)
            └─ MicrophoneTestSession — "Test Microphone": mic → system default output pass-through + input level + record/playback of a clip; owns lifecycle, permission mapping, restarts, recorder phases (observes AudioDeviceControl for the input id)
                 ├─ MicrophoneEngine (internal protocol) — AVFoundation/HAL/TCC execution, no policy
                 │    ├─ AVAudioEngineMicrophoneEngine (AVAudioEngine on a private aggregate of mic + default output, see below)
                 │    └─ ScriptedMicrophoneEngine (test target only)
                 ├─ ClipRecorder (internal: the locked PCM buffer the input tap records into)
                 └─ AudioLevelMeter (pure RMS → dBFS → 0...1 meter math) + LevelThrottle (internal: ≤25 Hz decimation)
macmic-cli (probe / solid / cycle / blink / audio — thin executable over QuadcastKit)
  └─ MicrophoneTestRun (`audio test`: drives a MicrophoneTestSession, prints phase lines and a 10 Hz meter through TestTerminal)
```

- `QuadcastKit` — library target, all protocol/HID logic, zero UI dependencies
- `MacMic` — executable, SwiftUI menu bar app, depends on `QuadcastKit`

- `Sources/QuadcastKit/Audio/AudioLevelMeter.swift` — `AudioLevelMeter` (`rootMeanSquare`, `normalizedLevel(rms:floorDecibels:)` — dB-linear from -60 dBFS to 0) and internal `LevelThrottle` (at most one value per interval, carrying the peak, nothing within epsilon of the last)
- `Sources/QuadcastKit/Audio/ClipRecorder.swift` — internal: fixed-capacity `AVAudioPCMBuffer` appended to from the I/O thread under an `NSLock`; `start(format:capacity:onFull:)`, and `append(_:)` hands `onFull` back exactly once, from the append that filled the clip; `append(_:to:)` is the pure copy (both interleavings, refuses mismatched layouts, stops at capacity — no roll-over)
- `Sources/QuadcastKit/Scheduler.swift` — `Scheduler` (`now`; `schedule(after:on:_:)`, which never runs the action inline, even for 0; extension `schedule(after:_:)` on main and `scheduleRepeating(every:on:_:)`, which re-arms before running), `ScheduledWork` (idempotent, thread-safe cancel) and `DispatchScheduler` (production: `systemUptime` + `DispatchWorkItem`)
- `Sources/QuadcastKit/FrameStreamer.swift` — the resident display loop: every `interval` (`defaultInterval` = 55 ms) on the `Scheduler`, sends header+data packets on an internal serial queue (re-arming before each send against the run's own deadlines, so neither a slow transfer nor timer lateness stretches the period — see the comment in `fire`); `setMode` swaps the frame sequence (same `LightMode` keeps the playback position), `start` (a no-op while running) / `stop`; `onError` (the streamer has stopped itself) and `onFirstFrameSent` (once per run) are delivered on main through the scheduler

### Testing approach

- Unit tests only (Swift Testing framework via `swift test`); no e2e/UI framework — state logic lives in the concern objects (`Lighting`, `LightingSettings`, `AudioControls`, `MicrophoneTest`) and `MicrophoneTestSession`; views stay thin and have no tests of their own.
- Pure protocol/frame logic (`QuadcastPacket`, `Frame`, `PresetSequencer`) is tested against byte-exact reference vectors derived from `reference/QuadcastRGB/`.
- Device/streamer logic is tested against `MockHIDTransport` — never the real `IOUSBHostTransport`, which is hardware-only and exercised manually via `macmic-cli probe`. The mock tracks functions in the production `QuadcastFunctionSet` (entry id = product id): `autoConnectOnOpen` matches `0x171f` then `0x171d` (two `onDeviceConnected` calls, like hardware), `simulateConnect(productID:)` (default `0x171f`) matches one function, `simulateRemoval(productID:)` terminates one (`onDeviceRemoved` only if it was the last), `simulateUnplug()` terminates all; sends throw `deviceNotFound` while no function is matched and `sendFailed(kIOReturnError)` while only `0x171d` is (as on hardware); `nextSendError` fails one send, `persistentSendError` every send until cleared, and `sendAttempts` counts every call, failed ones included. Send order and the removal rule are tested directly in `QuadcastFunctionSetTests`.
- Lighting is tested through `Lighting` + `MockHIDTransport` + `ManualScheduler` + `TestDefaults`, built by `LightingFixture` (`relaunch()` on the same defaults with a fresh transport; `tick(n)` advances one `FrameStreamer.defaultInterval` per tick, which runs the send and delivers `onError`/`onFirstFrameSent` before returning; `persisted` is the slot's persistent domain). `FrameStreamerTests` drive the streamer the same way, plus a `LateScheduler` wrapper that runs every action late (the only way to see cadence drift on a manual clock) and one wall-clock test on `DispatchScheduler`; there is no test-only tick entry point. `LightingSettingsTests` test the settings value directly.
- Audio-control logic is tested through the interface. `CoreAudioDeviceControlTests` run the real `CoreAudioDeviceControl` over `FakeHAL` (an in-memory device list with the QuadCast's element layout; listeners fire asynchronously on their queue, writes are echoed to listeners, reads/writes/listener registrations can be made to fail) via `CoreAudioFixture` (private callback queue, `DeliveryRecorder`, `settle()` = drain the control's queue, then the callback queue). `AudioDeviceControlContractTests` run one contract against both `CoreAudioDeviceControl` + `FakeHAL` and `MockAudioDeviceControl` (`@Test(arguments: ControlKind.allCases)`); app tests use the mock (synchronous deliveries, ids `4100`/`4101` on present directions, `simulateReenumeration`, `registrationsAtOpen`). `AudioControlsTests` build `AudioControls(control: mock)`, then `mock.open()`, as `AppState` does. Only `SystemHAL` is hardware-only, exercised via `macmic-cli audio`.
- Code that schedules through `Scheduler` is tested with `ManualScheduler` (`advance(by:)` runs due actions in (due time, scheduling order), including ones scheduled meanwhile, `.main` actions inline and others via `queue.sync`; `runUntilIdle()`; `pendingCount`). Suites that use it with main-queue actions, or that touch main-thread-only types, are `@Suite @MainActor`.
- Mic-test logic runs the real `MicrophoneTestSession` in every test, over `MockAudioDeviceControl` + `ScriptedMicrophoneEngine` + `ManualScheduler`, built by `MicrophoneTestFixture`. The scripted engine records every call, answers from scripted values (`access`, `preparation`, `settlesAfterPolls`, `startResult`, `canAllocateClip`, `recordedDuration`, `playbackPosition`), invokes callbacks only from test-facing triggers (`answerAccessPrompt`, `emit`, `fillRecording`, `emitPlaybackLevel`, `finishPlayback`, each with a `…Previous…` twin that delivers a stale callback from an ended run/recording/playback), and records an `Issue` when the session breaks a port precondition. `StatusLog` (attached by default) fails a test on an invariant break, a repeated status, or a non-zero level outside `.running`. `MicrophoneTestSessionTests` cover the session, `MicrophoneTestTests` the app model, `MicrophoneTestRunTests` the CLI run (into a `RecordingTerminal`); `AVAudioEngineMicrophoneEngine` is hardware-only, exercised via `macmic-cli audio test`. `AudioLevelMeter`, `LevelThrottle` and `ClipRecorder` are tested directly against known sample buffers.
- Each concern is tested without the rest of the graph; only `AppStateTests` (composition: open order, sleep/wake fan-out, teardown, independent lighting/audio presence, what is persisted) build `AppStateFixture` (mock `transport` and `audioControl`, the real session over a scripted engine, one `ManualScheduler` shared by the session and the lighting, a private `NotificationCenter`, `persisted`, `relaunch()` on the same defaults, `releaseState()`). Its `UserDefaults` come from `TestDefaults`, a pool of reused `dev.alavreniuk.macmic.tests.slot<N>` suites: every unique suite name leaves a plist in ~/Library/Preferences, so never create per-test suite names.

## Hardware notes

This is important context for any future protocol/transport work — see the plan's Task 5/6 for the full investigation:

- `IOHIDManager`/`IOHIDDeviceSetReport` **cannot** reach the QuadCast S's vendor-page (`0xFF0B`) report handler on this class of Mac. Only a Consumer Control HID service (`usagePage 0x000c`) gets matched, and every report ID tried (`0`, `0x2A`, `0x2C`) at both 64- and 60-byte payload sizes was rejected with `kIOReturnError` (`0xE0005000`). An `IOHIDManager`-based transport was built for that investigation and removed (last present in 3592ff8); don't add one back without a new probe result.
- The working path is a raw USB control transfer via `IOUSBHostDevice` (`Sources/QuadcastKit/HID/IOUSBHostTransport.swift`), matching what QuadcastRGB does over libusb. `IOUSBHostObjectInitOptionsDeviceSeize` on device init is what lets it take over from the kernel-resident HID driver — no separate `IOUSBHostInterface` claim needed.
- Two USB functions enumerate for one physical mic: PID `0x171f` (accepts control transfers, `kIOReturnSuccess`) and PID `0x171d` (rejects, `kIOReturnError`). Always prefer `0x171f`. Because both are matched/removed independently, `QuadcastFunctionSet.remove` reports the set empty — and so `IOUSBHostTransport` fires `onDeviceRemoved` — only once *every* matched function is gone; firing on the first termination would spuriously disconnect the app while the other function (usually the working `0x171f`) is still present (see the `removingOnlyTheAudioFunctionKeepsLightingConnected` regression test). `onDeviceConnected` fires once per matched function, so twice per mic.
- The device does not persist color — streaming must never stop while lighting should stay on. `FrameStreamer` is a resident 55 ms loop, not a fire-and-forget configurator.
- `HIDTransport.open()` succeeding only means matching notifications were registered, not that a device is present: `IOUSBHostTransport` reports an already-matched device asynchronously via `onDeviceConnected` (`handleMatched` hops queue → main). `Lighting.isDevicePresent` must be set from that callback, never assumed true right after `open()` returns — see the `deviceAbsentAtLaunchLeavesLightingNotFound` regression test.
- `Lighting.wantsStreaming` must gate on `isDevicePresent` as well as `settings.isEnabled` (and not asleep): a settings change racing a hotplug-removal notification must not resume the streamer against a device that just disappeared.
- Presence and send health are separate: a failed send (e.g. only `0x171d` matched) keeps `Lighting.isDevicePresent` and the controls enabled, shows "QuadCast S not responding — retrying", and retries with a capped backoff for as long as lighting is wanted. Only `onDeviceRemoved` marks the mic gone (see `removingOnlyTheControlFunctionMarksSendFailingButKeepsPresence`).
- **Audio (Core Audio HAL, not the vendor USB protocol).** The mic enumerates as *two* Core Audio devices, both named `HyperX QuadCast S` / manufacturer `Kingston` / transport USB, with `kAudioDevicePropertyModelUID` = `HyperX QuadCast S:0951:171D` on both. `CoreAudioDeviceControl` matches on that ModelUID suffix (`:0951:171d`, compared case-insensitively) and falls back to the name only when no ModelUID is reported. The two devices are told apart by `kAudioDevicePropertyStreamConfiguration` channel counts per scope (2 in / 0 out = microphone, 0 in / 2 out = headphone monitoring), not by the `DeviceUID` suffix (`…:4100:1` / `:2` are just enumeration order).
- Audio is the `0x171d` USB function — the one that *rejects* lighting control transfers — so audio presence and lighting (`HIDTransport`) presence are independent hotplug lifecycles; `AudioControls` availability is never derived from `Lighting.isDevicePresent` or vice versa.
- Per scope (input for the mic, output for monitoring): `kAudioDevicePropertyMute` is on element 0 (main) only; `kAudioDevicePropertyVolumeScalar` / `VolumeDecibels` are on elements 1 and 2 (per channel) and **not** on element 0. `CoreAudioDeviceControl` writes every channel with the same value and reads channel 1. Do not add an element-0 volume fallback without a probe result for a device that needs it. Observed dB ranges: input -8…+7 dB, output -40…-9 dB. `kAudioDevicePropertyDataSource` is absent on both devices.
- The HAL quantizes a written volume scalar (USB audio volume is in 1/256 dB steps; e.g. writing 0.812 reads back 0.81217885) and its listener echoes the quantized value. `AudioControls` (private `reconcile`) treats an incoming volume within `AudioControls.echoTolerance` (1%) of the current one, with the mute bit unchanged, as that echo and keeps the slider value (taking only the fresh dB); everything else — availability, mute, larger deltas — takes the incoming value. `CoreAudioDeviceControl.refreshSnapshot` separately dedups on levels + device ids; delivery is latest-value.
- Verified 2026-09-05 via `macmic-cli audio`: gain/mute/monitor/monitor-mute writes all took effect and read back; an external write from an independent Core Audio process was delivered through `onStateChanged` (since replaced by `observe(_:)`) on the main queue within ~1 s; `close()` removed every listener with `noErr`.
- Audio hotplug verified 2026-09-05 by re-enumerating the audio function in software (`IOUSBHostDevice.reset()` on PID `0x171d` — only possible while MacMic is *not* running, since its transport holds that function exclusively): `CoreAudioDeviceControl` delivered `.unavailable` ~30 ms after the reset, the devices came back ~2 s later under new AudioObjectIDs (`110/102` → `196/188`), listeners were re-registered on the new ids (proven by the control then reporting macOS restoring the saved gain: the mic re-enumerates at gain 0.80 and coreaudiod writes the remembered 0.68 back ~0.7 s later — the mic does not persist gain across re-enumeration), and a write/readback/`close()` afterwards were clean. A physical unplug/replug takes the same `kAudioHardwarePropertyDevices` path. **Whether host-side mute lights the mic's red mute LED has not been observed** (the CLI check was run without eyes on the mic) — treat it as unknown until someone records the observation here.
- **Test Microphone (AVAudioEngine pass-through, `Sources/QuadcastKit/Audio/AVAudioEngineMicrophoneEngine.swift`; policy in `MicrophoneTestSession.swift`).** The Mac does the routing: capture from the QuadCast's Core Audio *input* device, play through whatever the system default *output* is (AirPods, a headset, the display's speakers), and meter the input. The obvious design — set `kAudioOutputUnitProperty_CurrentDevice` on `inputNode.audioUnit` to the mic and leave `outputNode` on the default output — **does not work on macOS**: `inputNode.audioUnit == outputNode.audioUnit` (verified by pointer equality), so binding the shared unit to the input-only mic moves the output there too and `engine.start()` fails with -10875 (`kAudioUnitErr_FailedInitialization`, `IsFormatSampleRateAndChannelCountValid(outputHWFormat)`). The adapter instead creates a *private* aggregate device (`kAudioAggregateDeviceIsPrivateKey`, main sub-device = the default output, drift compensation on the mic) via `AudioHardwareCreateAggregateDevice`, binds the unit to that, and destroys it on every teardown. Don't try to go back to the direct bind. Each sub-device is declared with only its own direction (`kAudioSubDeviceInputChannelsKey: 0` on the output, `kAudioSubDeviceOutputChannelsKey: 0` on the mic) — the composition AVAudioEngine's own `CADefaultDeviceAggregate` uses (read back through `kAudioAggregateDevicePropertyComposition` on 2026-09-06: `channels-in`/`channels-out` per sub-device). The HAL then creates the output device's input streams with `kAudioStreamPropertyIsActive = 0`; verified 2026-09-06 with the Microsoft Teams loopback device (in=1/out=1) as the output sub-device: the aggregate's second input stream came up inactive and AVAudioEngine ran 2 s on it with a 2-channel input format and 20 tap buffers. Without those keys the output device's input streams are part of the aggregate and get run — the AirPods restart storm below.
- Before building the aggregate, the engine's `prepare` pins the mic's `kAudioDevicePropertyNominalSampleRate` to the output's rate when the mic supports it, and the session polls `isSettled` (20 ms, max 1 s) for the readback before `start`. Something on this Mac (Teams) parks the QuadCast at 16 kHz; under a 48 kHz aggregate the HAL restarted the aggregate's I/O ~3.5 s in and `AVAudioEngine` stalled in a configuration-change storm, while pinned to 48 kHz it ran clean for 10 s repeatedly. **The pinned rate is deliberately not restored on stop.**
- Restart triggers (coalesced per main-queue turn in the session, each restart re-reading the input id from the control and passing through `.starting` again — as one value carrying any clip — before `.running` with the new output name): `.AVAudioEngineConfigurationChange` only when `engine.isRunning == false` (the engine posts one with the engine still running right after `start()`), a `kAudioHardwarePropertyDefaultOutputDevice` listener registered in `prepare` (the aggregate names a specific output, so the engine cannot follow AirPods on its own; a trigger while still settling restarts the start), and a `CoreAudioDeviceControl` delivery whose input id differs from the one the run was bound to. The engine has no device-list listener of its own: mic loss arrives as a control delivery without an input and fails the test (`.failed(.inputDeviceUnavailable)`, in one status with the clip dropped and `isInputAvailable` false); a device-list change that leaves the input id alone does nothing. Input validation before start: `DeviceIsAlive` + input channel count > 0, and a non-zero channel/rate input format after binding. The session's private `RestartLimiter` allows `restartLimit` (3) restarts per `restartWindow` (10 s); the next one ends the session in `.failed(.engineFailed("output device <name> keeps changing its audio format"))` instead of restarting — a failure, so the clip is dropped. `<name>` is the output this session last ran on ("the output device …" if it never reached `.running`). `start` resets the count and that name. Covered by the restart tests in `MicrophoneTestSessionTests` (`fourthRestartWithin10sFailsNamingTheOutputAndDropsTheClip`, `restartsSpacedBeyondTheWindowKeepRunning`, `startResetsTheRestartBudget`, …).
- QuadCast HAL `AudioObjectID`s are reassigned whenever the audio function re-enumerates (observed repeatedly during the 2026-09-05 session: input 130 → 127 → 128 → 116 while a `dist/MacMic.app` instance ran concurrently; early -10851 `kAudioUnitErr_InvalidPropertyValue` failures were stale ids). The session reads the input id from the control's snapshot at start and on every restart; never cache it anywhere else.
- TCC: the bundle's `Info.plist` **must** carry `NSMicrophoneUsageDescription` (authored in `scripts/make-app.sh`, asserted by `scripts/test-make-app.sh`) — macOS kills an app that opens the mic without it. Permission is requested through `AVCaptureDevice.authorizationStatus(for: .audio)` / `requestAccess`; denied or restricted → `.failed(.microphoneAccessDenied)`, and the Audio page points at System Settings. An unbundled `swift run macmic-cli` binary inherits the terminal's microphone permission: on 2026-09-05 `authorizationStatus` returned `.authorized` for the terminal-run CLI, no TCC dialog appeared, and there was no denial or crash for the unbundled CLI without `NSMicrophoneUsageDescription`. The bundled-app permission path (the dialog on first "Test Microphone" click in `dist/MacMic.app`) has **not** been exercised.
- Feedback: playing the mic through speakers in the same room as the mic is a feedback loop. The feature exists for headphones/AirPods/a headset; the UI and README say so, the code does not try to detect it.
- Verified 2026-09-05 (macOS 15.7.9, Xcode 26.1.1, QuadCast S present as PIDs `0x171d`/`0x171f`) via `macmic-cli audio test`, quoted from the run log: `.build/release/macmic-cli audio test --seconds 4` → "testing microphone (input device 116) for 4 s…" (the CLI no longer prints the input device id), "starting…", "running: playing through LG HDR 4K", meter refreshed ~10 Hz in place and moved with ambient noise between `[....................]   0%` and `[#####...............]  23%`, then "stopped", exit 0. `swift run -c release macmic-cli audio test --seconds 8` → same three state lines, 81 meter redraws in 8 s, no restart, exit 0 (run twice). Scratch-program evidence for the design: private aggregate created with `noErr` (in=2 out=2 @48 kHz); with the mic pinned to 48 kHz, 10 s runs against both the built-in speakers and the default output delivered ~10 tap buffers/s with non-zero varying RMS and zero `AVAudioEngineConfigurationChange` restarts; with the mic at 16 kHz the aggregate's I/O restarted at ~3.5 s and the engine stopped ~0.5 s later. **What this proves is only that the engine started, ran to completion, and the level meter tracked the input.** Nobody spoke into the mic during these runs (ambient noise only), and whether audio was actually audible on the output device was not checked by ear — treat pass-through audibility as unverified until someone records it here.
- Record/playback verified 2026-09-06 via `.build/release/macmic-cli audio test --record 3`: "running: playing through LG HDR 4K", "recording for 3 s — say something…", meter suffix advanced `recording 0.0 s` → `2.3 s`, "recorded 3.0 s", "playing back…", meter switched to the clip (`playing 0.1 / 3.0 s` at 2%, then 0% — ambient noise only) through `3.0 s`, "playback finished", exit 0. The `AVAudioPlayerNode` was attached at engine build and connected to the main mixer at first playback while the engine was running, which worked; `.dataPlayedBack` completion fired on its own. Same caveat as above: nobody spoke and nobody listened, so whether the clip is audible on the output is unverified.
- **AirPods as the default output (restart storm, 2026-09-06).** With "Andrii's AirPods Pro #2" as the system default output, `.build/release/macmic-cli audio test --seconds 8` printed "starting… / running: playing through Andrii's AirPods Pro #2" five times in 8 s, Record captured 0 frames or a 1.0–1.4 s clip cut off by the restart. A HAL listener alongside showed the only events: the AirPods output device's `kAudioDevicePropertyNominalSampleRate` flipping 48000 → 24000 → 48000 about every 1.2 s, each flip also firing output-scope `kAudioDevicePropertyStreamConfiguration` (no device-list or default-device change). Cause: the aggregate was built from the whole AirPods device, so their microphone stream was run too, which puts the Bluetooth link into the hands-free profile (24 kHz); the rate change restarted the engine, the restart destroyed the aggregate (back to 48 kHz), the new aggregate ran the mic stream again. Fix: the `channels-in = 0` composition above. **The fix has not yet been verified against the AirPods themselves**: they disconnected before the fix was built and did not reconnect during the session (a scratch IOBluetooth connect attempt was not permitted), so the evidence is the Teams-loopback aggregate above and Apple's own composition; the LG HDR 4K case re-verified after the change (`--seconds 8`: one starting/running pair, 80 meter redraws, zero HAL events on the listener; `--record 3`: recorded 3.0 s, played back, exit 0). If the AirPods still flap, the `RestartLimiter` ends the test after the 4th restart in 10 s with the failure text above instead of looping; the next thing to try is `kAudioStreamPropertyIsActive = 0` on the aggregate's extra input streams after creation (settable, verified with the Teams device) or preferring an output-only AirPods HAL device if one enumerates.
- Not exercised on hardware: switching the system default output while running (e.g. to AirPods; the coalesced restart path) and unplugging the mic while running (a control delivery without an input → `.failed(.inputDeviceUnavailable)`); the system default output being itself an aggregate or multi-output device (`AudioHardwareCreateAggregateDevice` may refuse nesting — surfaces as `.failed(.engineFailed("could not create aggregate device (status)"))`).
- Polar pattern is a physical knob on the QuadCast S with no software interface; nothing in the code attempts it.
- `FrameStreamer.setMode()` only resets `frameIndex` to 0 when `LightMode` itself changes, not on brightness-only calls: `Lighting` calls `setMode` on every settings change, brightness included (e.g. once per `Slider` drag tick), so without this a `.cycle`/`.blink` animation would restart from frame 0 on every tick of the brightness slider instead of just dimming in place — see the `brightnessOnlyChangeDoesNotResetPlaybackPosition` regression test.

## Conventions

- Every source file (Swift and shell) carries a GPLv2 header. `QuadcastPacket.swift`, `Frame.swift` and `PresetSequencer.swift` in `Sources/QuadcastKit/Protocol/` additionally credit Ors1mer/QuadcastRGB, since that logic is a direct port. Every other file — including `HID/`, `FrameStreamer.swift`, `Audio/` and `Sources/macmic-cli/` — carries the plain GPLv2 header with no credit line. See any existing file for the exact header text.
- License is GPLv2-only (not "or later") — matches the upstream QuadcastRGB license this project's protocol layer is ported from.
- `QuadcastKit`'s version-info enum is named `QuadcastKitInfo`, not `QuadcastKit` — a same-named type would shadow the module when a file also imports AppKit (which transitively defines an unrelated global `RGBColor` via Quickdraw, so `QuadcastKit.RGBColor` needs the module name to resolve unambiguously). Likewise QuadcastKit's `Scheduler` collides with Combine's, so a MacMic file that imports Combine writes `QuadcastKit.Scheduler`.
- SwiftUI on macOS answers a control's `.accessibilityLabel` / button title as `AXDescription` (and `AXAttributedDescription`) on request but does not list it in `AXAttributeNames`, so System Events' `title`/`description` show "missing value"/"button" for every SwiftUI button even though VoiceOver reads the label fine — verify labels with `AXUIElementCopyAttributeValue(element, "AXDescription")` from a scratch program, not with System Events (checked 2026-09-06 on the Audio page: Start Test, Record, Play, Input level all answered). A `Slider` gets its name only from a `LabeledContent` title (`AXTitleUIElement`); a slider that stands alone in a `Section` (Brightness, Speed) needs an explicit `.accessibilityLabel`.
- App is unsandboxed by necessity (raw HID/USB vendor-page access); distributed via GitHub releases, not the Mac App Store.
